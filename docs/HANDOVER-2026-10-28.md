## 0. 一句话

自启动不走注册表 Run 键，而是 `schtasks` 注册的登录计划任务 `SparrowAutostart`（`/SC ONLOGON /RL HIGHEST`）。
本机 `settings.json` 里 `start_with_windows: true`，但系统里**任务不存在**：任务被另一份 `start_with_windows=false` 的副本启动时**无条件删除**，而删除/创建失败全部只 `eprintln!`（GUI 无控制台，等于丢失），设置页又只读配置文件里的布尔值 —— 三者叠加，形成「UI 说开着、系统没有、永远不报错」。

## 2. 根因

### 2.1 实现链路

| 环节 | 位置 |
|---|---|
| 任务名常量 | `src-tauri/src/services/settings_service.rs:11`（`SparrowAutostart`） |
| 旧任务名 | 同文件 `:15`（`ClipboardManagerAutostart`） |
| 创建 | `enable_autostart()`：`schtasks /Create /TN … /TR "\"<exe>\" --minimized" /SC ONLOGON /RL HIGHEST /F` |
| 删除 | `disable_autostart()`：`schtasks /Delete /TN … /F` |
| 启动时收敛 | `src-tauri/src/lib.rs:334` → `migrate_autostart_task()`（每次启动都跑） |
| 设置落盘 | `settings.json` 的 `app_settings.start_with_windows`（`<exe目录>/config`） |
| 前端开关 | `src/components/SettingsPanel.tsx`，`checked={settings.start_with_windows}` —— 只读配置，不查系统 |

> 旧版历史文档 `HANDOVER-2026-10-22.md:209` 描述的是「设置开着但任务丢了就自愈」；6f58cc7（改名 2.0.0）把这段改成了 `migrate_autostart_task`，**新引入了「设置为 false 时无条件删除任务」的分支**。

### 2.2 四个缺陷

| 编号 | 缺陷 | 后果 |
|---|---|---|
| D1 | 删除不校验归属：不看任务当前指向哪个 exe | 任何一份配置为 `false` 的副本（便携版/开发构建/换目录）启动一次，就删掉正式安装版的任务 |
| D2 | 失败被吞：`eprintln!` 后仍 `Ok(())`；且设置先落盘再同步 | 「配置说开、系统没开」永久共存，前端永远拿到成功 |
| D3 | 创建后不回查；UI 不查系统状态 | schtasks 返回 0 就当成功；任务被清理后设置页无任何提示 |
| D4 | `load_settings` 反序列化失败回落默认值（`start_with_windows=false`），`migrate` 随即删任务 | 配置文件一旦读不动，自启动被静默清掉 |

### 2.3 时间线与推断

1. 10-26 02:09 用户在设置页拨动开关，`settings.json` 写入 `true`；
2. 此后 10-27 18:50 构建了 1.1.1，仓库根副本的 `config` 是 `false`；
3. 该副本只要被启动一次，`migrate_autostart_task` 就无条件 `schtasks /Delete` 把 `SparrowAutostart` 删掉；
4. 正式安装版从 10-26 02:09 后未再启动，自愈逻辑没有机会执行 → 开机无自启。

> 任务计划 Operational 日志已关闭，无法 100% 坐实删除者；上述是与全部证据自洽的唯一解释。修复不依赖这个结论——D1 已从根上堵死该路径。

### 2.4 已排除

- ❌ `/TR` 引号拼装错误：用与 Rust 完全相同的参数行非提权 `/SC ONCE` 创建成功，动作字符串正确。
- ❌ exe 未提权 / 清单丢失：`mt.exe` 提取 RT_MANIFEST #1 为 `requireAdministrator`。
- ❌ 注册表 Run 项被 UAC 静默跳过：本应用不写 Run 键。
- ❌ d98ea88（identity 修复）引入：只改 `EXPECTED_IDENTITY_VERSION` 常量。
- ❌ 安装目录变化：安装器原地升级，仍在 `D:\clipboard`。

## 6. 部署注意事项

1. **版本号重编号带来的降级坑**：已装 2.1.0/2.1.1（旧编号）的用户安装 1.x 包时，NSIS 的 SemverCompare 判定为「降级」，默认 `allowDowngrades=false` 会要求先卸载。
2. **`allowDowngrades` 在本仓库使用的 Tauri CLI 版本里不可配置**：写进 `tauri.conf.json` 的 `bundle.windows.nsis` 会被 schema 拒绝（`is not valid under any of the schemas`），因此本次没有改配置；同版本（1.1.1 → 1.1.1）走「重新安装」是当前最省事的落地路径。
3. **安装器不会创建自启动任务**：`nsis-hooks.nsh:155` 只删旧任务名；新任务靠应用启动时的 `migrate_autostart_task` 或设置页「立即修复」。
4. **安装路径原地保留**：`nsis/installer.nsi:549` 注释与逻辑确认旧 `config/data` 不删（`RMDir "$INSTDIR"` 非递归，目录非空即保留）。

## 7. 遗留风险

1. **schtasks 输出编码**：中文安装路径下 `<Command>` 若以 GBK 输出，UTF-8 解码会乱码 → 比对失败 → `enable_autostart` 返回 Err。方向是安全的（不会误删），但这类用户会开不了自启。根治需启用 `windows` crate 的 `Win32_Globalization`（MultiByteToWideChar）或引 `encoding_rs`。
2. **`cargo fmt` 会污染全仓**：仓库本身不是 rustfmt-clean，跑一次会重排 27 个无关文件（约 +1293/−360 纯格式噪声）。只对单文件跑 `rustfmt <file>`。
3. **disable 查询失败即 Err**：若查询任务被拒绝访问，关闭开关会失败并弹窗（而不是假装关掉）。正常提权进程不会触发。
4. **`--minimized` 启动时完全不建窗口**（`lib.rs:352`）：只有托盘图标，容易被误判为「没启动」。排查时先看进程/日志。
5. **仓库根的旧构建**：`sparrow-setup.exe`（`82945f18…`）与 `sparrow.exe` 仍是 10-27 发布版，不含本次修复；不要把它们当成修复版分发。
6. **`migrate` 每次启动都会重建任务**（`/F` 幂等）：会重置任务的「上次运行时间」等元数据，属可接受的既有行为。

## 11. 追加事故（2026-10-28 晚）：稀疏包被注册到 debug 目录

### 11.1 现象

开机弹窗：

```
Windows 找不到文件
'D:\copy\clipboard-manager-tauri\src-tauri\target\debug\sms-helper.exe'
```

### 11.2 根因

稀疏包 `ClipboardManagerIdentity` 的注册表项里：

```
HKCU\...\AppModel\Repository\Packages\ClipboardManagerIdentity_0.2.1.5_neutral__z0fnhbkv2vcxr
  PackageRootFolder = D:\copy\clipboard-manager-tauri\src-tauri\target\debug
```

即**包的外部内容目录指向调试构建目录**（某次 `tauri dev` 注册的）。而 `identity.rs` 的 `registered_version_matches()` 只比对版本号（0.2.1.5 == 0.2.1.5）→ 判定「已注册、可直接用」→ 永远不会从 `D:\clipboard` 重注册。

安装版在 `D:\clipboard` 运行，但激活 `sms-helper` 时按 AUMID 解析到包根目录，也就是 debug 目录。10-28 凌晨清理空间时删除了 `target\debug`（18 G），helper 文件随之消失 → 应用启动到短信服务时激活失败，Windows 弹出「找不到文件」。

### 11.3 修复

**系统层（已执行，立即生效）**

```powershell
Remove-AppxPackage -Package ClipboardManagerIdentity_0.2.1.5_neutral__z0fnhbkv2vcxr
Add-AppxPackage -Path 'D:\clipboard\clipboard-identity.msix' -ExternalLocation 'D:\clipboard' -ForceUpdateFromAnyVersion
```

结果：`Status=Ok`、`PackageRootFolder = D:\clipboard`。

**代码层（防复发）**

- `registered_version_matches()` 增加第二重判断：读 `PackageRootFolder` 与当前 `exe_dir()` 做目录判等（`normalize_dir`：统一分隔符/小写/去 `\\?\`/去尾部斜杠）。不一致 → 返回 false → `reregister_if_stale()` 触发 `force_reregister`。
- 读不到注册表值、或根目录在 `C:\Program Files\WindowsApps` 下（非稀疏安装）时退回旧行为，避免每次启动都重注册。
- 新增 3 条单测（大小写/斜杠/`\\?\`/尾部斜杠、debug 目录必须判不等）。

### 11.4 验证

- `cargo test --lib` → **284 passed / 0 failed**（原 281 + 新增 3）
- `cargo check --example sms-capture-helper` → 通过（identity.rs 被 `#[path]` 复用到 example，新增依赖 `winreg` 是既有直接依赖，未引入新 crate）
- 系统侧：`PackageRootFolder = D:\clipboard`，`D:\clipboard\sms-helper.exe` 存在

### 11.5 教训

1. 稀疏包与安装版共用同一个包名/版本，**谁先注册谁定义包根目录**；调试构建会顶掉安装版的注册。
2. 清理 `target` 前先确认包根目录是否指向它：`reg query "HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\CurrentVersion\AppModel\Repository\Packages" /s /f "ClipboardManagerIdentity"`。
3. 与 §4.5 同类：`AppxManifest.xml` 的 Version 与 `identity.rs:205` 仍需手工同步；本轮新增的「根目录」校验至少能兜住路径错位这一类。
