迁移前的构成：v0.1.0–v0.4.4 共 23 个、v1.0.0–v1.4.3 共 10 个、v2.0.0/v2.1.0/v2.1.1 共 3 个。

操作顺序（重要，避免撞名）：

1. 先建 `v0.5.0` – `v0.9.3`（这 10 个名字原本空着）；
2. 再"腾空"被旧 1.x 占用的 `v1.0.0` / `v1.1.0` / `v1.1.1`（删旧 Release + 删远端 tag + 删本地 tag）；
3. 建新 `v1.0.0` / `v1.1.0` / `v1.1.1`；
4. 最后删其余 10 个旧 tag：`v1.0.1`、`v1.2.0`、`v1.3.0`、`v1.4.0`–`v1.4.3`（7 个），以及 `v2.0.0` / `v2.1.0` / `v2.1.1`（3 个）。

| 项 | 处理方式 |
|---|---|
| `v1.0.0` 资产 | 用原 `v2.0.0` 的二进制 |
| `v1.1.0` 资产 | 用原 `v2.1.0` 的二进制 |
| `v1.1.1` 资产 | **重新构建的新产物** |
| 其余 10 个 0.x | 用原 1.x 二进制原样搬运 |
| tag 类型 | `v0.9.1`（原 v1.4.1）是唯一的轻量标签，其余为附注标签；重建时保持类型不变、指向原 commit |
| 附注 tag message | 按映射改写（例：`v2.1.1: 修复粘贴目标错位与连续粘贴问题` → `v1.1.1: …`） |
| commit message | **保持原样**（仍是 `chore: release 2.1.1` 等），改写要重写 git 历史 |
| Latest | 已设为 `v1.1.1` |

- 代价：13 个被重建的 Release **下载计数归零**、资产上传时间变为重传时间；二进制字节未变（v1.1.1 除外，它是新构建的）。

## 4. identity 修复（重点章节）

### 4.1 症状与根因

| 项 | 值 |
|---|---|
| 不一致点 A | `src-tauri/src/services/identity.rs:205` 的 `EXPECTED_IDENTITY_VERSION = (0,2,1,4)` |
| 不一致点 B | `src-tauri/identity/AppxManifest.xml:7` 的 `Version="0.2.1.5"` |
| 引入提交 | `6f58cc7`（`feat: rebrand to Sparrow / 剪雀 2.0.0`） |
| 该提交做了什么 | 清单 `0.2.1.4` → `0.2.1.5`，`Executable` 从 `clipboard-manager-tauri.exe` 改成 `sparrow.exe`，**但漏改 identity.rs 的常量** |
| 为什么这次才炸 | 这次 bump 的本意正是触发强制重注册，漏改把意图完全抵消 |
| 上一次为什么没事 | `c94e534`（0.2.1.3→0.2.1.4）是两边一起改的 |

### 4.2 影响方向（容易误判，写清楚）

| 机器状态 | 四元组比较结果 | 实际行为 |
|---|---|---|
| 本机（注册 0.2.1.4） | 相等 → 判定"匹配" | **永不刷新**，改名后的新清单永远部署不上 |
| 全新机器（注册 0.2.1.5） | 不等 → 判定"不匹配" | **每次启动都卸载 + 重装一遍 MSIX**，启动延迟 1–3 秒、部署日志 churn |

### 4.3 调用链路

`sms_code_service.rs:163` 首次 `NotificationChanged` 订阅失败（无包身份，`0x80070490`）
→ `identity::ensure_identity_registered()`
→ `identity::reregister_if_stale()`
→ `registered_version_matches()`：用 WinRT `PackageManager::FindPackagesByNamePublisher` + `pkg.Id().Version()` 做四元组严格 `==`
→ 不等则 `force_reregister()`（`RemovePackageAsync` 全部卸载 + `AddPackageByUriAsync` 重装）。

### 4.4 修复与验证

- 修复：`identity.rs:205` 常量改为 `(0, 2, 1, 5)`，一行。
- 验证（已实测）：`Get-AppxPackage -Name ClipboardManagerIdentity` 从 `0.2.1.4` 变为 **`0.2.1.5`**，`Status: Ok`、`SignatureKind: Developer`。
- 包内清单：`ClipboardManagerApp` 的 `Executable` 已是 `sparrow.exe`，`SmsHelper` 仍是 `sms-helper.exe`。

运行时日志的正常形态：

```
[sms-code] NotificationChanged 订阅失败(无包身份应用的已知限制),尝试注册稀疏包身份: 找不到元素。 (0x80070490)
[sms-code] 稀疏包身份已注册,但当前进程无身份,激活 sms-helper: 找不到元素。 (0x80070490)
[sms-code] sms-helper 已激活 (pid=51900),本线程进入监工模式,捕获由 helper 负责
```

第二行的 `0x80070490` 是**预期**的：身份在进程创建时确定，重注册无法让已在运行的进程获得身份；主程序带 `requireAdministrator`，Shell 激活只支持中等完整性，不能重启自己，所以改用 `asInvoker` 的 `sms-helper.exe` 去持有身份（代码注释见 `sms_code_service.rs:188-196`）。

判断标准：看到 `sms-helper 已激活` 就说明链路正常；看到 `激活 sms-helper 失败,降级为 1s 轮询` 才是问题。

### 4.5 遗留风险

这是"两处手工同步"的隐性约定：下次改 `AppxManifest.xml` 的 `Version`，**必须同步改 `identity.rs:205`**。根治方案（本次未做）：用 `include_str!("../../identity/AppxManifest.xml")` 解析版本，做成单一数据源，约 15 行改动。

## 7. 已知影响与遗留

1. **已装 2.1.1 的老用户收不到更新提示**：`update.rs:86-96` 是手写三元组比较，`has_update = version_tuple(latest) > version_tuple(current)`，`1.1.1 > 2.1.1` 不成立。数学上无解，只能靠 Release 公告 / 手动下载。
2. **蓝奏云 <https://wwbwp.lanzoul.com/b00ybd8mej>（密码 `bdlx`）未更新**，新安装包需手动上传。
3. 历史 Release 下载计数归零（见 §3）。
4. `identity.rs` 与 `AppxManifest.xml` 的版本仍需手工同步（见 §4.5）。
5. `docs/superpowers/**` 里的旧版本号（如 `v1.3.0`）**未改**：其中有断言脚本与 HTML 字面量耦合，改动风险高于收益。
6. `src-tauri/target/release/bundle/nsis/` 目录仍保留各历史版本的产物（含 `Sparrow_2.0.0/2.1.0/2.1.1` 与 `clipboard_*.exe`），属本地构建残留，未跟踪、无影响。
